# Global Stack & Operational Rules

## Code Quality & Conventions
- **JavaScript/TypeScript**: Prefer modern ES modules and native browser/Node APIs over adding new dependencies; avoid `var`, prefer `const`/`let`.
- **Python**: Enforce type annotations, strict error handling, and clean CLI arguments.
- **Bash**: Write POSIX-compliant or clean Bash scripts with strict error flags (`set -euo pipefail`).
- **HTML**: Use semantic elements, proper ARIA attributes where native semantics fall short, and valid nesting.
- **CSS/SCSS**: Prefer Tailwind utility classes over custom CSS; use `tailwind.config` theme values (colors, spacing, etc.) instead of arbitrary values like `[#123456]` or `[13px]` unless there's no equivalent token. Reserve actual CSS/SCSS for things Tailwind can't express (complex animations, third-party overrides); keep any custom CSS specificity low and avoid `!important`.
- **Odin**: Maintain explicit context management, explicit memory allocation/deallocation, and clean package imports.
- **Makefile**: Use `.PHONY` for non-file targets, tabs (not spaces) for recipe indentation, and keep targets small and composable.

## Workflow & Operations
- **Git**: Follow Trunk Based Development with short-lived branches. You are not permitted to run `git commit` or `git push` (permission denied). When work is ready, remind the user to commit and append 'Closes #[ID]' to the final commit message so GitLab auto-resolves the issue.
- **Code Search**: When you need real-world examples of how to use a specific API, library, or error handling pattern, use the `gh_grep` tool to search public GitHub repositories for prior art. NEVER use `webfetch` directly on `raw.githubusercontent.com` or `github.com` URLs (unauthenticated requests trigger immediate HTTP 429 rate limits). If you must fetch a full source file discovered via GitHub search, rewrite the URL to use the jsDelivr CDN mirror: convert `https://raw.githubusercontent.com/:user/:repo/:branch/:path` to `https://cdn.jsdelivr.net/gh/:user/:repo@:branch/:path` (or use authenticated `gh api` via bash if available).
- **Git Repository History & Blame**: NEVER use raw bash commands (`git log`, `git blame`) or `grep` to investigate repository history or authorship. You MUST use the local `git` MCP tools. This ensures deterministic, safe, and easily parsable outputs.
- **Project Tracking & GitLab Issues**: When asked about the status of a project, pending work, or specific ticket details, you MUST use the `gitlab` MCP server to query live data. Do not guess or rely on outdated context. Read issues directly from `https://git.cstaf`.
- **Memory & Handbook**: Before implementing complex features, ALWAYS search the `handbook.wiki` (available via the `handbook` project reference). Never update the handbook merely because you changed code. Update it only when a durable architectural decision, convention, or discovered constraint is worth preserving.
- **Delegation**: Proactively use the `task` tool to delegate specialized work to subagents instead of doing it yourself (e.g., `tester` for writing tests, `refactor` for code cleanup, `dba` for database migrations — note that specialized subagents are defined per-project: `tester` and `refactor` exist in sigtaf-frontend and sigtaf-backend; `dba`, `reviewer`, `security-reviewer` exist only in sigtaf-backend; `e2e` exists only in sigtaf-frontend; `analyst` exists only in the documentation repo; delegate by name only when the current project defines that agent). **Exception for `researcher`:** Delegate to `researcher` ONLY if the investigation is complex and requires multiple tool calls across different documentation sources (e.g., combining Firecrawl + Context7 + gh_grep). If it is a simple lookup requiring only one tool call, perform the tool call directly to save time. If a task requires multiple distinct skills, orchestrate them by calling the task tool multiple times.
